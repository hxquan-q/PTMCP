# Git、变更评审与版本规范

版本：1.0-design · 2026-10-23。当前文档工作不自动创建提交、推送或发布；后续实现按本规范组织。

## 1. 分支与工作区

默认分支保持可构建。短期分支采用 `xquan/<type>-<topic>`，如 `xquan/feat-scoped-table-binder`、`xquan/docs-ptmcp-baseline`；用户显式指定名称时遵循用户要求。多人/代理并行时分配文件或模块所有权，修改共享契约先协调，不回退他人变更。

开始前检查git status和差异，识别已有未提交内容；不能用reset/clean或整体覆盖来清理他人工作。新worktree只用于明确隔离需求，不把未提交文件悄悄遗弃在旧目录。

## 2. 提交约定

采用 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/)：`type(scope)!: 中文或英文具体动作`，scope 与 ! 均可选，类型为feat/fix/docs/refactor/test/build/ci/chore/perf/revert。scope使用模块ID或docs域；一条提交解决一个可评审问题。功能与大规模重排格式分开提交，不能把安全行为变化藏进refactor。

提交消息由 `scripts/verify_commits.py` 机械校验（随 `scripts/check.py` 运行）：类型必须在白名单内，标题不超过 72 字符，禁止私钥、平台令牌和脱敏占位符。历史提交不改写；本地默认检查 HEAD，CI 只检查本次推送或 PR 的范围。

```text
docs(architecture): 明确主库安全状态与五秒撤销边界
fix(guard): 保留派生表同名情况下的物理关系绑定
test(authz): 覆盖重复刷新触发授权族撤销
feat: 新增个人查询历史入口
feat(api)!: 调整REST响应契约
```

描述说明问题、最终行为和验证证据。只有格式调整可以不扩展测试；涉及ACL、SQL、认证或取消的修复必须先增加能暴露问题的测试。

破坏性变更使用 `!` 或正文 `BREAKING CHANGE: 原因及迁移方式`，不能仅写 refactor 隐藏。后续可从 feat/fix/perf 与 breaking 标记生成发布说明，生成后仍核对用户影响；当前未安装/执行自动版本或发布工具，不因提交前缀自动发布。

## 3. PR 内容与评审

PR包含目标/触发场景、变更边界、FR/ADR/TC关联、实际执行的检查、证据链接和未验证项。引用依赖版本/客户端兼容性时附锁定构件与记录，不用“最新版本”“全部已测”等不可核查表述。

小而完整的纵切优先；大型改动拆成可顺序合入的依赖PR。安全关键变更需认证/SQL/数据负责人评审。数据库迁移需说明前后版本共存和回滚，修改scope/令牌/审计策略需同步ADR和运维手册。

## 4. 禁止提交内容

数据库密码、真实PAT/平台secret、私钥、浏览器会话、生产原SQL/结果、个人敏感信息、私有VQ/skills资产不能进入开源仓。Reference下载源码用于阅读，不将整个参考仓与构建缓存混入PTMCP提交；许可证移植记录与少量自有PoC另按归属管理。

不提交target/dist/node_modules等产物。需要分发的schema/契约/迁移属于源码，应版本管理；构建镜像、日志和测试证据按发布证据策略存储，不用二进制堆积代替可复现构建。

## 5. 合入与发布

合入前同步默认分支，运行与变更匹配的检查；冲突按最终业务行为解决，不能盲选ours/theirs。保护默认分支，禁止强推共享历史。CI检查必须与本地同规则，不允许仅CI跳过关键测试。

发布采用SemVer：破坏API/MCP语义为major、兼容新增为minor、兼容修复为patch。当前只有设计版本1.0-design，不等于软件v1.0.0已发布。正式发布使用不可变tag与镜像digest，并生成面向使用者的changelog。

紧急安全修复仍保留最小回归与审批证据；灰度失败先按运维回滚/关闭功能开关，不篡改既有tag。存在不可逆迁移时不能以回退镜像代替数据恢复方案。

## 6. 文档变更规则

总体方案管跨域不变量；PRD管业务验收；后端契约管字段/API；ADR解释决策。变更同一规则必须更新引用方，不能另写一个“最终版”制造平行基线。历史review和证据保持原样，仅由新基线说明纠正/覆盖点。

文档PR运行链接/围栏检查，明确设计、已实现、已测试、已部署四种状态；只有证据支持时才能升级状态。任务完成勾选以实际验收为准，不能把“文档已写好”标成“功能已完成”。

开发入口、任务合同和验收分层见[Agent 开发流程](agent-workflow.md)。适用的工作项、契约和决策记录随实现同批更新；获准提交时纳入同一变更。归档冻结及决定翻转遵循[笔记政策](decision-notes.md)，不以事后补记或重写历史代替证据。
