## 结论

**Java + Vue 的方向可以保留，但当前方案需要修改后再作为实施基线。最需要重估的是 SQL 授权内核与 OAuth 接入，不能把它们视为现成组件组合。**

最关键的反证已经复现：JSQLParser 5.4 原版 `TablesNamesFinder` 会因为同名派生表别名、嵌套 CTE 而漏掉真实表。方案多次写到的“自动正确处理同名遮蔽，可以直接拿来做 ACL”不成立。改写后只执行 final_sql，也不能消除这个缺口。

另外，Spring Security 7.1.2 默认不给授权码流程下的公开客户端签发 Refresh Token；mcp-security 0.1.14 默认仍使用同一个生成器。因此，“接上这套组件即可让各桌面客户端自动续期”需要专门实现或调整验收。

建议保留薄网关、独立 guard、只执行 final_sql、数据库只读账号、admin 与 gateway 隔离这些选择。先完成下面的 P1 验证，再细化 9～10 周交付承诺。

## R1 · P1：撤回“TablesNamesFinder 能直接用于安全 ACL”的结论

**位置**：方案第 253、276～291、440、589 行。

本次复现：

```sql
SELECT s.*
FROM salary s
CROSS JOIN (SELECT 1 AS n) salary;
```

这条 SQL 读取物理表 `salary`，但原版 `new TablesNamesFinder<>().getTables(ast)` 返回 `[]`。AST 重生成仍然是这条查询。如果实现按“提取出来的每一张表都在授权集合中”判定，空集合会让这一关无检查对象。数据库共享只读账号通常具有比单个用户更大的 SELECT 范围，因此只读账号也不能补足用户级表授权。

原理不是解析失败，而是提取器把派生表别名加入全局 `otherItemNames`，最后从表集合中统一删掉这些名字；它没有按 SQL 作用域区分这两个 `salary`。嵌套 CTE 也有同类结果。即使把空集合一律拒绝，仍需解决名字消除缺陷，不能据此宣称表提取已正确。

同版本 sources jar 的关键位置：`TablesNamesFinder.java` 第 256～262、340～349、358～369、523～529 行。实现结构也可从[官方源码](https://raw.githubusercontent.com/JSQLParser/JSqlParser/jsqlparser-5.4/src/main/java/net/sf/jsqlparser/util/TablesNamesFinder.java)核查；具体输出以本次下载的 Maven 构件为准。

**修改建议**：继续使用 JSQLParser 做语法解析，但自行实现带作用域的物理关系绑定器。区分 CTE 定义与使用、非递归 CTE 体内的同名物理表、派生表别名、相关子查询和集合运算分支；无法确定绑定时拒绝。原版 Finder 只能作辅助比对。

**验收**：复现证据中的 4 个反例都必须识别到 `salary`；拒绝时执行器调用次数为 0；常规 CTE 不误报。将物理表显式限定到已验证的 schema/database 后，再验证 final_sql 中的对象与授权对象一致。这个工作应从 M1 前移到 M0。

## R2 · P1：统一资源身份与数据库对象解析，避免“检查 A，执行 B”

**位置**：方案第 438～440、482、532、571～573、589 行；REQ 第 58～62、82～85 行。

当前接口只有 `database_name`，池按 `datasource_id` 建立，guard 又用 `defaultDb` 补全表名。方案没有写清：两个数据源都有同名数据库时如何定位；PG 的 database 和 schema 如何区分；执行连接如何确保使用同一个默认命名空间。

例如 guard 依据入参把 `orders` 记成 `erp.orders`，而 PG 连接仍用默认 `"$user", public`，数据库可能执行 `public.orders`。MySQL 池若复用到另一个 catalog，也存在相同的不一致。系统库黑名单仅检查显式 schema 也不完整：本次探针中 `SELECT * FROM pg_authid` 只被提取为 `pg_authid`，不会自动带上 `pg_catalog`。单靠这个探针并未证明 ACL 可被绕过；它证明名称还没有完成数据库语义上的绑定。

PG 的名字解析遵循 search_path，且 pg_catalog 默认隐式参与。见[PG schema 与 search_path 文档](https://www.postgresql.org/docs/18/ddl-schemas.html)。本地 dbx 已为此维护独立处理逻辑，见 [postgres.rs:8526](C:/Users/xquan/Desktop/Datachat-mcp/Reference/dbx-main/crates/dbx-driver-postgres/src/postgres.rs:8526)，不能只搬元数据 SQL 与连接池参数。

**修改建议**：

1. Tool 使用稳定的 `datasource_id` 和命名空间标识；可保留展示名称，但不要仅凭名称路由。
2. 资源键至少包含 datasource、catalog/database、schema、object，并保留引号语义。PG 大小写折叠、MySQL lower_case_table_names 按实际服务器配置处理。
3. guard、ACL、Schema 缓存和执行器共享同一份经过验证的执行上下文；把物理表引用改写为正确限定名，不能只给检查用的字符串补前缀。
4. 每次借连接时验证/设置相应状态；归还时清理事务、catalog/schema、超时与会话状态。Hikari 的物理连接初始化不等于每次请求初始化。

**验收**：两个数据源同名库表、PG 两个 schema 同名表、引号大小写、系统表无 schema 引用、连接池跨命名空间复用全部覆盖。测试不仅断言提取出的名字，还要断言实际执行的数据库对象。

## R3 · P1：默认公开客户端不会获得 Refresh Token

**位置**：方案第 360、367、461、618 行；REQ 第 52 行。

Spring Security 7.1.2 的 `OAuth2RefreshTokenGenerator.generate()` 检测到授权码流程的客户端认证方法为 `none` 后返回 null；授权了 refresh_token grant 也不会改变这个分支。见[官方同版本源码](https://raw.githubusercontent.com/spring-projects/spring-security/7.1.2/oauth2/oauth2-authorization-server/src/main/java/org/springframework/security/oauth2/server/authorization/token/OAuth2RefreshTokenGenerator.java)。

mcp-security 0.1.14 的默认配置仍然实例化这个生成器，没有自动改变这项策略。见 [McpAuthorizationServerConfigurer](https://raw.githubusercontent.com/spring-ai-community/mcp-security/v0.1.14/mcp-authorization-server/src/main/java/org/springaicommunity/mcp/security/authorizationserver/config/McpAuthorizationServerConfigurer.java)。

不能由此断言所有目标客户端必然失败：它们实际使用 `none`、动态注册密钥还是其他认证方式，还需联调。但这足以否定“框架支持刷新令牌，因此四个桌面客户端都能自动续期”的推导。CIMD/公开客户端这一类必须单独处理。

**修改建议**：将 OAuth 的可行性验证前移到 M0。逐个记录注册方式、token_endpoint_auth_method、PKCE、回调 URI、token 响应和过期后的行为。公开客户端可以选择标准重新授权体验；如果无感刷新是硬要求，则明确支持的安全扩展、轮换/重放检测、撤销机制及客户端兼容性。不要靠把共享 secret 写进桌面配置来解决。

**验收**：至少一个 `none + S256` 的公开客户端和一个受信服务端客户端跑完真实流程；短时 access token 到期后再次调用，并验证刷新或重新授权行为。若实现 refresh rotation，还要验证旧 refresh token 重用和并发刷新。

## R4 · P1：平台身份需要可验证的调用方证明

**位置**：方案第 373、384、479、570、577 行；REQ 第 45～47 行。

方案已经认识到 IDE 明文 secret 的问题，但把 WorkBuddy `staticHeaders` 与真正的服务端注入并列为最高信任，把可验证的 CIMD 域名视作平台身份，这两点仍需收紧。

[WorkBuddy 官方文档](https://open.workbuddy.cn/docs/connector)对 staticHeaders 的说明是“不展示给用户且不可编辑”，这不足以证明凭证只保存在受信服务端。CIMD 则提供客户端标识和元数据；[MCP 客户端注册规范](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/basic/authorization/client-registration.mdx)仍允许使用 `token_endpoint_auth_method: none`。能够获取同一个公开元数据，不等于证明请求来自指定平台后端。

因此，如果按这些信号给一个“可信平台”更大的 Scope，第三方可能自行复用 client_id/配置，再用自己的用户身份取得同样的平台归属。token 内的 platform_id 只能保护已签发字段，不能修复签发时把平台认错的问题。

**修改建议**：将“客户端逻辑分组”与“可密码学验证的平台调用方”分开。公开/DCR 新客户端默认进入最小 Scope；管理员建立平台映射。只有经核实的后端代理凭证、mTLS、private_key_jwt 等可验证机制，才能获得相应的受信等级。平台归属由服务器决定；Header、PAT 绑定和 OAuth claim 不一致时拒绝，不能让 Header 覆盖 token。

**验收**：伪造平台名、复制公开 client_id、注册同名 DCR 客户端、修改 Header、把同一 PAT 放到另一个平台调用，都不能扩大有效权限。WorkBuddy 未完成凭证保管位置验证前，不能仅凭 staticHeaders 升级信任。

## R5 · P1：统一用户停用、授权到期与令牌撤销的生效机制

**位置**：方案第 538、557、568～578 行。

缓存仅描述“授权变更时 bump 版本号”，但权限还随时间、用户状态、角色状态、部门归属与树结构变化。例如一项 grant 的 valid_to 到期时，没有人修改授权，缓存仍可能继续持有旧表集合。角色变更和用户停用也不是 acl_grant 更新事件。

本地若依 [SysUserController.changeStatus](C:/Users/xquan/Desktop/Datachat-mcp/Reference/RuoYi-Vue-Plus-6.X/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/controller/system/SysUserController.java:270)调用 [updateUserStatus](C:/Users/xquan/Desktop/Datachat-mcp/Reference/RuoYi-Vue-Plus-6.X/ruoyi-modules/ruoyi-system/src/main/java/org/dromara/system/service/impl/SysUserServiceImpl.java:370)只更新数据库状态，没有 PTMCP 权限版本、OAuth/PAT 撤销或网关通知。

新 OAuth 登录若只复用密码哈希核对，也会遗漏若依已有的停用检查和失败锁定。原实现见 [PasswordAuthStrategy.java:69](C:/Users/xquan/Desktop/Datachat-mcp/Reference/RuoYi-Vue-Plus-6.X/ruoyi-admin/src/main/java/org/dromara/web/service/impl/PasswordAuthStrategy.java:69)及该文件第 113～124 行。共享 sys_user、Redis，不会自动共享这些行为。

**修改建议**：

- 缓存具有策略版本与时间边界，TTL 不超过下一次 valid_from/valid_to；考虑新表同步、删除重建、平台停用和 Scope 变化。
- 用户停用/删除、改密、角色/部门变化、grant 变化、PAT 吊销进入统一失效清单；定义事件提交、投递、网关检查与补偿方式。
- JWT 每请求配合用户状态/认证版本检查，或采用合适的 introspection 方案；明确最大撤销延迟和故障行为，不能只靠 access token 自然到期。
- 登录校验服务统一覆盖账号状态、密码算法、失败锁定与审计；AS 的刷新流程也检查账户有效性。

**验收**：在有效 access token、refresh token、PAT 与热缓存都存在时停用用户；分别测试变更角色、移动部门、grant 自然到期、丢失通知和 Redis 故障，结果满足书面约定的生效时间。

## R6 · P1：字节上限与超时取消必须落实到驱动和连接生命周期

**位置**：方案第 532、591、645～646 行。

“setMaxRows + 边读边计字节”尚不能保证 JVM 内存上限。[MySQL Connector/J 文档](https://dev.mysql.com/doc/connector-j/en/connector-j-reference-implementation-notes.html)说明默认 ResultSet 完整取回并存入内存；[pgJDBC 文档](https://jdbc.postgresql.org/documentation/query/)也说明默认一次性收集结果。即使只有 500 行，甚至只有一行，大 TEXT/BLOB 或字符串表达式仍可能在应用计字节之前耗尽内存。

此外，MySQL 的 cancel/queryTimeout 需要另一条连接执行 KILL。若超时工作已返回、业务连接已归还，而取消命令随后才到达，就可能干扰该连接上的下一次查询。方案中的“超时就 KILL”还不足以描述安全归还条件。

**修改建议**：

- 在实际驱动版本下配置并验证增量获取。PG 游标需要正确事务模式和 fetchSize；MySQL 明确使用行流式或经过验证的游标模式。处理大字段时避免先 getString/getBytes 全量复制再截断。
- 定义单元格、总结果、并发请求和进程的内存预算；对于驱动仍需物化的单行数据，补充数据库/驱动约束与处理策略，不能把“流式”当成任意大单元格的完整保护。
- 定义 checkout、连接、查询、取消、清理的独立超时；请求结束到取消/回滚确认前持有连接，状态不确定时淘汰连接。PG 使用自身取消机制，不套用 MySQL KILL 语法。
- 配置每数据源及全局池预算、用户/平台/数据源的并发和排队限制。多副本总连接数按“池数 × 每池上限 × 副本数”核算。

**验收**：大字段、多行、并发读取的实际 JVM 峰值内存有界；取消后数据库执行确实停止，连接无残留事务；构造“查询刚结束、取消迟到、下一请求开始”的竞争，下一请求不得被误杀。

## R7 · P2：把静态只读证明的边界写清，并补类型与函数绑定规则

**位置**：方案第 224、588、639、655 行。

dbx 已明确警告：只读证明是 UI 启发式，PG 自定义 operator/cast 和 MySQL UDF 能隐藏静态语法看不到的行为。见 [sql_risk.rs:923](C:/Users/xquan/Desktop/Datachat-mcp/Reference/dbx-main/crates/dbx-sql-core/src/sql_risk.rs:923)。同时，它拒绝带限定路径的函数及表函数，见该文件第 1435～1457 行；移植不应只带走裸函数名单。

本次 `SELECT CAST('x' AS public.leaky_type)` 能正常解析，属于已允许的 CastExpression，但不是普通 Function 节点。只允许 CAST 这个节点名，不能证明目标类型相关的数据库代码安全。这里没有创建自定义类型或执行泄露实验，属于需要约束的边界，不标记为已验证绕过。显式 `OPERATOR(public.+)` 样例本次解析失败，按原方案应拒绝。

**修改建议**：限定可用类型和类型转换；明确 schema 限定函数、重载解析、表函数、扩展及 operator 的政策；固定可信名字解析环境，检查执行账号对自定义代码的可用权限。连接的数据库定义应受管理员信任与变更治理。数据库只读事务主要兜底写入，不能自动等同于用户表级读取隔离。

## R8 · P2：把共享模块边界与依赖对齐做成可检查的约束

**位置**：方案第 429、529～539 行。

本地若依 [pom.xml:23](C:/Users/xquan/Desktop/Datachat-mcp/Reference/RuoYi-Vue-Plus-6.X/pom.xml:23)实际使用 Boot 4.1.1、Spring AI 2.0.1；方案建议 4.1.2/2.0.2。这是需要验证的补丁升级，不是版本不存在。本次已取得 Boot 4.1.2、Spring AI BOM 2.0.2、mcp-security 0.1.14 与 JSQLParser 5.4 的对应构件。

更实际的冲突是若依 [ruoyi-common-mybatis/pom.xml:25](C:/Users/xquan/Desktop/Datachat-mcp/Reference/RuoYi-Vue-Plus-6.X/ruoyi-common/ruoyi-common-mybatis/pom.xml:25)直接依赖 ruoyi-common-satoken，同时依赖 mybatis-plus-jsqlparser。Maven Central 的 [MyBatis-Plus 3.5.17 POM](https://repo.maven.apache.org/maven2/com/baomidou/mybatis-plus-jsqlparser/3.5.17/mybatis-plus-jsqlparser-3.5.17.pom)引用 JSQLParser 5.2，而 guard 计划用 5.4。若公共模块复用整个若依 MyBatis 层，既可能带入另一版本解析器，也可能带回 Sa-Token 依赖。

## R9 · P2：为每次调用的审计补可靠性与敏感 SQL 处理

**位置**：方案第 489、592、602～606 行；REQ 第 103～104 行。

REQ 要求记录每次调用，但方案只写异步队列/Redis Stream，没有定义队列满、Redis 不可用、消费者停机、网关在执行后崩溃时如何处理。异步本身不是问题；缺少的是可接受的数据丢失量、持久化与补偿约定。

同时，sql_raw/sql_final 可能含姓名、证件号等字面量。把完整 SQL 保留并复制到其他日志系统，会扩大这些数据的可见范围。

**修改建议**：明确 request_id、开始/结束状态、重试去重、持久队列、积压上限、失败处理及告警。对于审计不可用时是否继续执行，应由产品需求明确。常规检索使用指纹/脱敏 SQL，确需保存原文时限制访问并加密，落实保留期和清理。用户门户只按服务器认证主体取历史。

## R10 · P2：修订错误语义、一期范围和验收材料

**位置**：方案第 98、265、594、616～621 行；REQ 第 59、71～90 行。

1. **工具拒绝语义**：把权限拒绝统一返回 isError=false 会让通用调用方将其视为成功。建议用结构化拒绝内容和明确的不可重试分类表达行为；已进入工具的业务执行失败通常以 isError=true 返回，身份认证失败则在 HTTP/OAuth 层处理。重试策略应在客户端约定，不能靠成功标记解决。参见 [MCP Tools 错误处理](https://raw.githubusercontent.com/modelcontextprotocol/modelcontextprotocol/main/docs/specification/2026-07-28/server/tools.mdx)。若决定拒绝属于业务正常结果，应在工具输出契约和监控中明确区分，不能仅凭 isError 统计成功。
2. **数据库范围**：REQ 涉及 SQL Server、Oracle，方案一期仅覆盖 MySQL/PG。建议正式写明一期仅支持哪两个方言，其余延期；不要让通用 datasource.type 选项承诺未实现的执行安全能力。
3. **元数据可见性**：REQ 已允许“可看无权表名、执行时拒绝”，这是产品选择，本次不将它误判为越权漏洞。但 meta/read 两种 action、隐藏开关和 get_table_schema 的行为需要统一；方案收紧了无权表列信息的返回，应同步验收规格。
4. **测试材料**：当前仓库无法重现文档声称的 java-poc 与 29 条 VQ。把 PoC 源码、构建锁定、用例 ID、参数渲染、预期输出、运行日志纳入可访问的证据包；内部 fixtures 留在内部仓可以，但必须明确交付位置。仅“29 条可解析”不能证明守门、权限和改写后的业务结果正确。
5. **排期与验收**：M0 就应覆盖资源绑定、表 ACL 和公开客户端认证，不能到 M1/M2 才验证这些主线假设。P95 <50ms 需注明 SQL 大小、并发、冷热缓存、硬件和计时范围。“无高危绕过”应表述为指定威胁模型、指定回归/模糊测试集未发现绕过，不能作为对全部 SQL 的安全保证。
