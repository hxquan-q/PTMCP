# PTMCP 运维手册

版本：1.0-design · 日期：2026-10-23 · 状态：待实现服务的运维设计与演练规范。

依据：[总体方案](../总体方案.md)、[部署手册](deploy.md)、[测试计划](../test/test-plan.md)。本文指标名是实现期须交付的观测契约，当前没有已上线仪表盘、告警规则或实测恢复报告。

## 1. 运行职责与安全状态

运维负责进程、网络、存储、监控、备份、发布与事件处置；数据源负责人负责业务账号、数据库负载和对象变更；组织授权管理员负责授权；安全管理员负责密钥与敏感审计。值班人员不得为排障临时放开所有表、跳过JWT状态核验、关闭审计或把数据库改成写账号。

日常检查应覆盖Nginx、admin/authz/gateway、MySQL主库、Redis、WAL持久卷、业务源及证书。liveness用于进程是否能自行恢复；依赖短暂异常不应引发无限重启。readiness/工具准入分别判断：能否确认安全状态、能否持久化审计START、是否还有执行预算。元库安全状态超过5秒无法确认时停止新查询，Redis健康不能代替主库确认。

所有时间戳存UTC；告警和工单展示Asia/Taipei并附原UTC。跨进程时效测量使用同步时钟和单调计时；时间漂移本身触发告警，避免授权边界或签名有效期判断漂移。

## 2. 监控指标与告警

指标不把userId、requestId、SQL、token、表名等高基数/敏感值当Prometheus标签；详情通过受控日志按requestId查询。数据源/平台标签使用受限稳定ID，避免可任意输入值膨胀。下表阈值是一期设计初值，需经容量测试调整并保留变更记录；安全上限不能为了消除告警而放宽。

| 指标契约 | 初始阈值与级别 | 首要动作 |
| --- | --- | --- |
| `ptmcp_security_snapshot_age_seconds` | >1秒告警观察；≥5秒严重并拒绝新SQL | 查元库主库可达性/延迟，不能续命旧缓存 |
| `ptmcp_security_epoch_mismatch_total` / 缓存重建失败 | 连续1分钟增长严重 | 查主库版本、事件消费与快照构造；旧快照不可放行 |
| `ptmcp_security_event_lag_seconds` | >30秒警告，>60秒严重 | 查outbox与Pub/Sub补偿；与5秒准入指标分开 |
| `ptmcp_audit_start_durable_failures_total` | 任意增加严重 | 停新SQL并查元库；确认被拒请求没有业务连接 |
| `ptmcp_audit_completion_durable_failures_total` | 任意增加严重 | 查结局DB/WAL；保持在途状态并告警 |
| `ptmcp_audit_outbox_oldest_age_seconds` | >60秒警告，>300秒严重 | 查消费者、锁、磁盘与入库错误 |
| `ptmcp_audit_wal_used_ratio` / 磁盘可用 | ≥70%警告、≥85%严重；无法写/fsync立即停止新SQL | 降低流量/扩容受控卷；不得删除未确认WAL |
| `ptmcp_audit_unknown_total` | 任意新增需调查 | 对照START与进程崩溃时间，不冒充SUCCESS |
| `ptmcp_query_internal_seconds` | 标准负载窗口P95≥50ms持续5分钟警告 | 看解析/ACL/元库审计准入span，排除口径混测 |
| `ptmcp_query_queue_size` / queue_wait | >24持续1分钟警告；到32或等待3秒产生拒绝 | 查并发/业务库慢查询；不能无界扩队列 |
| `ptmcp_query_active` / 各池等待 | 达配额或借池超时持续1分钟 | 核算源/全局/副本连接；降并发优先 |
| `ptmcp_query_cancel_seconds` / cleanup | 超3秒/2秒或取消后复用异常任意一次严重 | 淘汰不确定连接；隔离受影响源 |
| `ptmcp_connection_evictions_total` | >1%已执行查询或5分钟持续增加警告 | 查网络、取消与重置失败；不屏蔽淘汰 |
| `ptmcp_refresh_replay_total` | 任意新增安全事件 | family撤销，核对并发客户端/泄露；不自动恢复旧族 |
| `ptmcp_auth_failures_total` | 账号/IP速率异常警告 | 限速与失败锁定；日志不记录凭证 |
| JVM heap/RSS、GC、重启 | heap>75%持续5分钟警告；OOM/异常重启严重 | 关闭可疑宽行路径、降并发、检查驱动物化 |
| 元库连接/锁/磁盘、Redis内存/逐出 | 超批准容量或出现异常逐出警告 | 确认授权缓存和会话的故障行为，元库负载优先保障 |
| TLS/平台证书到期、签名钥轮换 | 到期前30/14/7天逐级告警 | 续期演练后切换，不临时关闭校验 |
| 备份/binlog归档/恢复演练 | 超预定间隔或失败即严重 | 修复备份链，必要时暂停变更 |

权限拒绝、语法拒绝和超预算属于verdict分类，不直接计入系统5xx故障率；但短时间激增可作为攻击/客户端行为告警。HTTP成功传输与工具`isError=true`分别统计，不以HTTP200掩盖工具失败。

## 3. 日常运维节奏

每工作日核对未处理严重告警、WAL/审计积压、最近备份与证书状态、数据源连接使用、异常family重放、UNKNOWN调用与安全版本年龄。每周抽查授权自然到期、用户停用/改密与PAT撤销，确认新查询在5秒边界内拒绝；抽查一条审计从START到结局的完整链。每月检查容量趋势、孤立数据源池、过期授权/令牌清理、180天审计清理任务、密钥访问记录与依赖升级计划。

Schema同步/字典注释更新按业务变更窗口执行。表删除重建、视图定义或类型变化提升资源版本并使受影响快照失效；不要沿用旧对象ID自动承接权限。DDL管理者属于受信边界，仍需先评估正在运行查询和角色权限的影响。

审计不保存查询结果作为长期历史；运维日志/heapdump可能间接包含内存数据，抓取前按敏感诊断流程处理，加密、限权和短期保留，禁止外发普通工单附件。

## 4. 故障排查与处置

### 4.1 新查询集中被拒绝或安全快照过期

按requestId确认错误发生在HTTP鉴权、工具守门还是系统准入。若snapshot age≥5秒，检查主库DNS/TLS、连接数、读锁和主从切换；权威确认只能读取当前主库。Redis恢复、收到心跳或缓存仍命中不是恢复依据。主库版本变化后，先重建相应权限/状态并确认新鲜，再恢复准入；不得重置时间戳而继续使用不匹配的旧权限。

若为真实授权拒绝，交组织管理员复核主体、有效角色/部门、Allow/Deny、有效期、平台Scope和对象版本；运维不能直接为用户扩大范围。

### 4.2 Redis不可用

确认MySQL安全状态与审计路径仍健康。权限缓存可降级为有界的主库查询，但须通过压测验证的限流；不能把降级变成主库洪峰。用户跨副本3并发依赖共享租约配额时，配额不可确认必须拒绝新SQL，不能因为主库正常就继续放行。admin/AS会话与锁定计数依赖Redis时按其契约拒绝认证，不允许验证码/失败锁定悄悄跳过。Pub/Sub丢失后通过outbox补扫恢复；5秒撤销边界仍由主库确认保障。Redis恢复后按版本重建，不将旧快照无条件回灌。

### 4.3 审计/WAL异常

START持久化失败立即停止新SQL；结局写库失败时仅在加密WAL fsync成功后才能确认持久。若WAL也失败，停止受理并尽力终止在途查询，保留已存在START为调查依据。检查磁盘/配额、inode、权限、key_id可用性、消费者积压与元库锁；不要通过删除WAL或改成内存队列恢复“可用性”。

恢复消费者后按request_id与事件状态幂等入库，验证事件完整与校验和，确认后才删除已确认段。崩溃遗留START由恢复任务标UNKNOWN并关联实例/故障窗口，不能自动重放业务SQL。发现WAL损坏隔离文件并保留证据，由安全/数据负责人决定修复，不跳过后宣称全量无丢失。

### 4.4 慢查询、取消异常与连接耗尽

先按阶段区分队列、借池、SQL、读取、取消、清理。15秒语句超时与30秒请求deadline是不同约束。停止向异常源新增查询，检查原数据库会话及取消任务是否仍在途。不能确认执行任务结束、语句关闭、回滚和状态恢复时强制淘汰物理连接；不要让其返回池中参与下一请求。

MySQL驱动可能使用额外连接取消，确认取消连接预算与网络；不部署可能晚到的自建KILL定时任务。PG使用自身CancelRequest与事务清理。业务DB管理员紧急终止会话时必须匹配源、用户、连接标识与请求阶段，事后核对误杀与审计，禁止按模糊进程名批量杀库。

若宽行引发内存压力，关闭未证明安全的类型/表达式路径、降并发并回放合成夹具定位。不要只减输出4KiB上限声称问题解决；检查驱动缓存、UTF-8/UTF-16复制、fetch批次和JSON序列化预算。

### 4.5 刷新重放/凭证泄露

确认family已经撤销，JWT状态核验也在5秒内拒绝。区分客户端并行刷新、响应丢失与疑似泄露，但旧RT无论原因都不能再次签发。指导用户重新授权；不得人工把CONSUMED记录改回ACTIVE。涉及用户凭证泄露时提升auth_version并撤销会话/PAT，改密不会将正常账号设DISABLED。仅在停用/删除账号时改变状态。

同时轮换受影响平台secret/签名钥/业务密码，范围以调查证据为准。日志保留requestId、clientId、familyId与原因，不记录raw token。安全事件沟通按组织既有渠道执行，本文不自动授权给外部人员发消息。

## 5. 备份、保留与恢复目标

以下为一期需实现并演练的目标，尚无实测达标结论。RPO/RTO以完整服务恢复计时，不用“数据库启动成功”替代安全状态和审计核对完成。

| 资产 | 备份/保护设计 | 目标与保留 |
| --- | --- | --- |
| MySQL元库 | 每日一致性全量备份+连续binlog归档，归档延迟≤5分钟；加密与跨故障域副本 | 目标RPO≤5分钟、RTO≤60分钟；全量35天，binlog至少覆盖最老可恢复全量 |
| 已确认审计START | 与元库事务/备份链保护；生产高要求需同步副本或等价持久方案 | 进程/单容器崩溃RPO=0；整存储故障受元库灾备RPO约束，不宣称无限零丢失 |
| 结局WAL | 独占持久卷+受控复制/快照；fsync后确认，入库确认前保留 | 进程崩溃不丢已确认段；节点/卷故障风险与复制间隔明确记录 |
| 签名/加密密钥 | 密钥管理系统版本化备份、访问审计与恢复演练 | 不可丢失；KEK/key_id保留到关联审计、WAL与备份全部过期 |
| 配置/发布manifest/UI | Git或受控仓库加版本；secret单独备份 | 每次发布前，保留可回滚的N-1及其依赖 |
| Redis | 有需要时AOF/备份；以主库重建权限缓存 | 不作权限权威；会话丢失可要求重新登录，不能恢复旧权限兜底 |

业务数据库备份由各业务负责人执行，不由PTMCP复制业务数据；本RPO/RTO只覆盖PTMCP自身元数据/审计与服务。MySQL备份工具、版本和一致性方法由运维实现选择并验证，不能把存在一个备份文件当成可恢复。

在线审计及归档保留180天，任务按UTC边界分批清理，避免大事务锁库。备份保留35天意味着已在线清理的数据仍可能在封存备份中延长最多35天；备份严格隔离、禁止日常查询，并随介质到期销毁。若组织要求180天为绝对物理删除期限，必须调整备份布局/选择性加密销毁与保留政策后再上线，不能默认声称已满足。安全事件合法保全需另行登记责任人、范围和期限。

## 6. 隔离恢复演练流程

1. 至少季度及重大存储/加密变更后演练一次；先记录故障时刻、目标恢复点、备份和binlog完整性、WAL段、key_id及预计数据损失窗口。
2. 在新隔离环境恢复MySQL全量并回放binlog到批准时间，校验migration版本、表计数/关键约束、用户状态、授权版本与audit_outbox；不要覆盖在线主库试错。
3. 恢复签名验证资料、解密密钥和WAL副本。由唯一恢复任务幂等入库结局事件，悬挂START标UNKNOWN；核对request_id重复/缺失，不重跑SQL。
4. 备份可能回退撤销状态，因此在恢复期间关闭所有token签发/查询准入。可采用全用户auth_version提升、撤销全部活跃RT family/PAT/Web会话并要求重新登录；若需保留凭证，必须有独立不可回退撤销记录可证明完整。不能从旧Redis恢复会话绕过这一步。
5. 清空/版本化重建权限缓存，让gateway从恢复后的主库确认安全快照；校验未来Deny与到期边界、平台Scope、对象版本及业务源实际只读权限。
6. 在隔离库执行允许/拒绝、JWT/PAT失效、审计START/结局、历史SQL解密和取消复用冒烟，测出实际RPO/RTO；数据负责人接受损失窗口后切换。
7. 逐步恢复流量，观察至少30分钟并记录恢复版本、异常、残留UNKNOWN与改进事项。未达目标登记缺陷和补救计划，不把演练写为PASS。

恢复记录应含证据哈希、各阶段开始/结束时间、抽查caseId、是否复活过期token、WAL缺口及负责人确认。目标60分钟若不达标先调整恢复流程/容量，不能事后改目标消除失败。

## 7. 密钥、证书与密码轮换

JWT签名钥使用kid，新钥先发布公钥→AS切换签发→验证所有gateway识别→旧access token最长10分钟加时钟偏差后停止普通验签使用；是否继续保留历史公钥按审计需要决定。疑似私钥泄露必须主动撤销相关family/提升版本，不能只等自然过期。

SQL/WAL加密使用AES-256-GCM信封加密并记录key_id，nonce按同钥唯一性保证。轮换KEK可重包DEK或迁移历史数据，必须测试旧记录、未重放WAL与封存备份可解。不得在180天在线保留结束时立即删除仍被35天备份引用的钥。

平台secret/mTLS证书采用服务端双版本短重叠、明确定时下线；重叠期两个版本均受平台身份与网络规则约束。数据库密码轮换建新池验证后切换并排空旧池；防止更新密码后让旧连接反复重连。TLS自动续期须监控失败并验证客户端证书链兼容。所有轮换和解密操作记录审计，secret不回显到界面或日志。

## 8. 发布、迁移与容量管理

发布按 [deploy.md](deploy.md)执行。数据库采用expand-contract：先兼容性增加表/字段/索引，再部署代码，等待回滚窗口和旧实例退出，最后单独批准删除/收紧。大表索引与180天审计清理在低峰验证锁/IO影响；schema migration失败时不启动忽略错误的实例。

扩容前核算所有datasource指向的实际数据库，计算查询池、取消连接、同步和其他业务预留。扩容后核对全局用户并发、权威快照确认负载、审计写与WAL吞吐；不能只按CPU HPA提升副本。空闲池回收要先确认无活动查询/取消任务，禁止直接关闭在用连接池。

保留发布前后配置差异、镜像digest、迁移checksum、灰度指标与回滚结果。安全修复回滚必须关闭受影响功能，不能恢复不安全行为。

## 9. 事件关闭条件

故障关闭前应证明：新查询准入恢复且安全状态新鲜；异常连接已淘汰/清理；审计积压已对账、UNKNOWN已登记；凭证撤销状态没有回退；监控恢复并维持观察窗口；对应TC回归通过；用户影响与数据风险已由责任人确认。纯HTTP200、进程重启成功或Redis恢复不构成完整恢复。
