# PTMCP 项目总体方案

版本：1.0-design · 日期：2026-10-23 · 状态：设计基线；部分能力已进入实现，M0 与完整系统验收仍需独立证据。

本文件统一跨文档的业务边界、技术决策、参数和状态语义。需求依据为 [review 修订意见](reviews/review.md)；原始 [REQ](REQ.md) 和 [选型调研](reference/PTMCP_开源选型与二开方案.md)保留为历史输入。本文不代表软件已经构建、联调通过或获准上线。

## 1. 产品目标与交付边界

2026-10-23 规范补充：开发标准采用[工程标准与门禁](standards/quality-tooling.md)；REST 线格式统一若依 R<T>（[ADR0010](architecture/adr/0010-REST响应复用R与模块错误码.md)），元库通用时间列统一 create_time/update_time，详见 API/数据库契约。本规范约束项目自有 SQL 的显式投影，不改变外部 SQL 的受控星号展开。以上为设计约束与当时的状态记录，不意味着所有条目均已实现或通过应用测试；现状以工作项和证据为准。

PTMCP 是权限管控型问数 MCP 安全网关：组织管理身份和数据权限，外部 Agent 负责推理与生成 SQL，网关负责元数据披露、静态校验、受控只读执行及审计。网关不调用大模型，不保存查询结果作为训练语料。

一期支持 MySQL 8 系列与 PostgreSQL 的受验证部署版本；候选集成环境为 MySQL 8.4、PostgreSQL 18，完整补丁号/驱动组合由 M0 构件清单锁定。Oracle、SQL Server、ERP 组织同步、列级权限、行级过滤、企业 SSO 和 Token Exchange 属于二期。只开放通过双引擎回归的数据库类型，不能因 JDBC 驱动可连接而宣传支持。

角色为平台管理员、组织授权管理员、安全审计员、普通员工。管理员的控制台菜单权限不自动赋予业务表读取权限；安全审计员也不自动拥有原 SQL 解密权限。所有人查询均执行平台上限与用户有效权限的交集。

组织授权管理员通过 `admin_delegation` 获得明确部门根、资源范围、动作与有效期；只有平台管理员能创建/撤销委派。委派不能由本人扩张，不能管理跨范围共享角色；管理菜单权限与资源委派必须同时成立。

组织授权管理员也不能通过给本人/所在角色或部门授权、调整成员关系、移除本人命中的Deny来增加自身META/READ。服务端比较命令前后本人有效权限，增权须由平台管理员另行操作。平台管理员也需显式业务授权才可查询，并保留操作审计。

## 4. 资源身份与权限契约

物理关系键为 `(datasource_id, catalog, schema, object_name)`。MySQL：catalog=database_name、schema 为空；PG：catalog=database_name、schema=schema_name。API 传输 ID 为字符串，避免 JS 整数精度问题。显示名不作为跨源唯一标识。

标识符同时记录原文、规范值及是否带引号，按数据库真实大小写规则绑定。PG 的 schema_name 在结构查询与 SQL 执行中必填；MySQL 这两个工具不接受非空 schema_name。未知表、Schema 快照过期、名字歧义或不支持节点均拒绝，不实时盲查业务库来“猜测”用户对象。静态拒绝不借业务连接。

Allow 来自个人、有效角色、配置启用的部门及上级部门；先按资源树展开继承，再应用时间区间 `[valid_from, valid_to)` 和 Deny，最后与平台 Scope 相交。READ Allow 隐含 META Allow；META Deny 同时阻断 READ；READ Deny 不自动阻断 META。默认无授权。平台/数据源停用优先于所有 Allow。

目录模式：`DISCOVER` 可在平台范围内披露表名和表注释并标记 `authorized`，但显式 META Deny 仍优先；`HIDE` 只显示有效 META/READ 的表。两种模式下只有有效 READ 才返回列、键和字段注释。二期列/行规则一期只预留模型，不声称已经实施。

资源READ集合与token工具Scope分别计算：`ResourceRead = UserRead ∩ PlatformRead ∩ ActiveResources`；查询需要ResourceRead与mcp:query，结构需要ResourceRead与mcp:schema，目录需对应目录Scope。schema-only PAT不会因缺少query Scope丢失资源READ资格，authorized标记资源可读性而不伪称该token能调用所有工具。

Schema 删除/重建、视图定义或授权对象变化均提升资源版本，旧快照授权不自动转移到新对象。数据库 DDL 管理员属于受信边界；DDL 与查询并发的数据库语义需在集成测试中约束，不能承诺仅凭字符串限定能对抗不受信 DBA 改表。

一期视图默认关闭；只有视图定义哈希一致、依赖图可完整解析、视图本身及所有底层物理关系均有有效 READ，且专项验收通过后才开放。目录中列出 VIEW 不代表允许执行，不靠 DEFINER 权限跳过底层授权。

## 5. 三个 MCP Tool 与 REST 边界

MCP 参数沿用 snake_case；新增控制台 REST 使用 camelCase。一期只注册以下三个工具：

| 工具 | 必需参数 | 可选参数 |
| --- | --- | --- |
| list_databases_and_tables | datasource_id | database_name、schema_name、keyword、cursor、page_size |
| get_table_schema | datasource_id、database_name、table_names（1～20） | schema_name（PG 实际必需） |
| execute_readonly_sql | datasource_id、database_name、sql_query | schema_name（PG 实际必需）、max_rows（只能收紧） |

list 的 datasource_id 必填，不支持按模糊库名搜索所有数据源。execute 的执行上下文由服务器校验，身份、平台和有效权限不能从 Tool 入参指定。成功结果包含列定义、类型安全的行数据、rowsReturned、truncated、截断原因和 requestId；DECIMAL/BIGINT 使用字符串，日期时间按显式格式输出，NULL 保留 null。

控制台新接口前缀为 `/api/v1/admin` 和 `/api/v1/me`；Web 会话接口 `/api/v1/session`。按照 ADR0010，管理/个人/会话 REST 统一复用实际若依 `R<T>` 的 `{code,msg,data}` 三字段：成功正文 code=200，错误 code 为登记的模块数字码，data 包含 requestId/errorCode/retryable/details。所有 REST 响应以 X-Request-Id 头返回服务端请求ID，不增加 R 的顶层字段。使用 HTTP 400/401/403/404/409/413/422/429/503 区分边界失败。OAuth 端点遵循标准协议，不套此 REST 包装；`/mcp` 使用 MCP JSON-RPC，也不套 REST 包装。

HTTP 认证/平台失败由过滤链返回 401/403。Tool 已开始后发生 SQL、表权限、危险函数、查询超时等失败，返回 `isError=true` 及结构化错误。权限/语法/非只读错误 retryable=false；短时系统不可用是否可重试由错误码定义，客户端必须限次退避，网关不自动重放 SQL。result、error、verdict 不混为一套统计。

## 6. 认证、平台证明与令牌生命周期

MCP access token 为 JWT：校验签名、iss、aud、exp、nbf、用户认证版本、授权族状态与平台；TTL 10 分钟。JWT 不携带可永久依赖的表权限集合。PAT 仅在创建时展示一次，随机高熵值以哈希存储，默认 30 天、最大 90 天；禁止放 URL。PAT 绑定个人终端平台，不可由 Header 提升为 Tier 1。

控制台采用独立 Sa-Token 服务端会话，适配为 HttpOnly、Secure、SameSite=Lax Cookie `PTMCP_ADMIN_SESSION`，所有写操作校验 CSRF；不将长效管理 token 存 localStorage。AS 登录使用独立会话 Cookie `PTMCP_AS_SESSION`，一期共用账号认证规则而不承诺跨应用 SSO。会话最长 8 小时。新密码12～64字符且UTF-8不超过72字节，以兼容若依BCrypt而不静默截断；错误 5 次锁 10 分钟，并配 IP/账号限速。

平台分 Tier 1 受信后端、Tier 2 管理的公开桌面客户端、Tier 3 个人终端。DCR 新客户端默认最小 Scope；public client_id/CIMD/隐藏 Header 不构成后端证明。Tier 1 除 AS 客户端认证外，每次 MCP 调用还需验证 mTLS 或经核实的后端代理 secret+网络约束；private_key_jwt 仅认证 token 端点，不自动证明后续 Bearer 请求来源。token/PAT 的 platform_id 不可被 Header 覆盖，冲突拒绝。

公开客户端续期采用专门扩展设计，默认关闭到 M0 验收通过。扩展包含 refresh 请求的 converter、公开客户端认证 provider、grant provider、token generator、持久化与撤销，不是只替换 generator。授权码须 S256、一次性 code、精确 redirect_uri；禁止向桌面下发共享 secret。

Refresh family 绝对寿命 30 天、空闲寿命 7 天，每次刷新原子消费旧 token 并轮换；存储 token 哈希及消费墓碑，直到 family 过期后清理。对同一旧 token 竞争仅一次成功；旧 token 再用会撤销整族及其 JWT，有效性不能只由 JWT 签名决定。不以“几秒内”无条件豁免重放；客户端需 single-flight，响应丢失/冲突后重新授权。无法兼容的客户端保留重新授权或 PAT 路径，不能假称已实现无感续期。

公开客户端标准撤销也需可达的NONE转换/认证/处理链：以client_id、token、token_type_hint核验token所属client/family，不能仅凭client_id撤销任意授权；无效/未知token按标准防枚举响应。introspection只开放给受信机密客户端。此处扩展需M0协议测试，不由refresh generator自动提供。

用户改密只提升 auth_version 并撤销会话/令牌，不将正常账号设为 DISABLED。停用/删除才改变状态。角色、部门、平台、授权和 Schema 变化分别更新对应版本。

## 7. 权限时效与安全事件

安全状态及 global policy epoch 在 MySQL 主库事务中更新，并同时插入 `sys_security_event` outbox。Redis Pub/Sub 用于快速通知；每 30 秒补扫事件用于恢复与补偿，不能作为撤销时限的保证。

所有副本采用 MySQL 主库确认的安全快照：本地缓存最多 1 秒，任何新查询使用的权威状态不得陈旧超过 5 秒；Redis 命中、消息心跳、层层缓存不能重置 `authoritativelyCheckedAt`。该时间从权威短事务首次读取发起前保守计龄，不能取慢查询完成时刻；读取完成已超过5秒则拒绝或重读。MySQL RR中同一读视图的两次epoch读取不能证明期间没有其他事务提交，如需检测并发变化必须使用明确的新读视图/current read。过期必须重新核验主库；主库无法确认则拒绝新查询。排队出队和 JDBC 提交前再次核验。由此目标为已提交撤销对新查询最大 5 秒生效；在途请求尽力取消，已返回数据无法收回。

有效权限集合缓存上限 300 秒，并截断到最近未来 valid_from/valid_to；命中时仍检查绝对 nextBoundaryAt 和当前安全版本。不得把即将生效的 Deny 排除在时间边界计算之外。自然到期不依赖通知消息。

## 8. SQL 守门与安全执行

流水线为：身份/输入预算 → Tool入口持久最小START → 词法预检 → 单 Select 解析 → 递归只读校验 → 函数/类型/表达式白名单 → 作用域关系与列引用绑定 → 权限交集 → 完全限定与 LIMIT 改写 → final_sql 重解析核对 → 确认同一审计准入并补充审批信息 → 最后状态核验 → 只读执行 → 完成审计与返回。START只含身份、工具、SQL哈希/长度等最小信息，不在解析前写未经脱敏SQL。

拒绝用户可执行注释、优化器 hint、多语句、赋值、写 CTE、锁、INTO、系统命名空间、表函数、带路径函数、自定义类型/操作符及未知节点。一期拒绝 WITH RECURSIVE、EXPLAIN/SHOW/DESC，结构访问走专用 Tool。允许经回归的普通 CTE、子查询、JOIN、UNION 与窗口表达式。长度预算外不进入解析；解析深度/时间由隔离任务和取消策略验证，不能依赖无限递归。

ScopedTableBinder 输出物理关系节点与列引用到关系的绑定。非递归 CTE 按方言作用域与定义顺序处理，派生表别名不从物理表集合删名。限定 FROM 关系时同步保持 `table.column`、`database.table.column`、`t.*` 与相关子查询的引用；优先保留原别名，生成别名时必须同步改写关联列。未知/歧义拒绝。guard 只返回不可由调用者自行拼装的 ApprovedQuery；执行器不接受原始 SQL 字符串的公共执行入口。

PG 顺序：借出干净连接 → setReadOnly(true)/setAutoCommit(false) → 确立 READ ONLY 事务 → SET LOCAL search_path TO pg_catalog、statement_timeout/lock_timeout → 执行 final_sql → 关闭结果与语句 → rollback → 恢复状态 → 归还。全部业务关系已限定，不将可写业务 schema 加入函数搜索路径。禁止在事务外执行 SET LOCAL 后声称生效。MySQL 使用明确只读事务及会话 max_execution_time，每次借还设置/清理。

执行状态为 `ACQUIRED → CONFIGURED → EXECUTING → DRAINING → CLEANING → RETURNED`；中断转 `CANCELLING`，不能确认终止则 `EVICTED`。取消完成信号必须包含原执行任务终止、语句关闭、回滚与状态恢复，不能只检查 cancel() 返回。MySQL 不维护可能晚到的应用自建 KILL 定时任务；任何取消任务尚在途时禁止复用连接。

## 9. 预算、审计与可运维性

| 参数 | 默认设计值 | 说明 |
| --- | --- | --- |
| SQL 输入 | 64 KiB UTF-8 | 另限 AST 深度 64、物理关系引用 64；M0 验证解析预算 |
| 行上限 | 500 | max_rows 只能收紧，覆盖外层 LIMIT/FETCH |
| 单格输出 | 4 KiB UTF-8/二进制 | 截断附元数据，不混写成真实 `[TRUNCATED]` 值 |
| 总响应 | 1 MiB 最终JSON-RPC响应UTF-8体 | 包含CallToolResult、列/行、structuredContent与text双份及二次转义；HTTP/TLS头不计 |
| 默认 fetchSize | 100 | 普通窄行初值，不是宽行内存保证 |
| 并发 | 用户 3；数据源/副本 8；gateway/副本 16 | 全局数据库连接预算另核算；排队每副本最多 32、最长 3 秒 |
| 超时 | 借池 3s、连接/网络兜底 20s、SQL 15s、取消 3s、清理 2s | 独立预算；socketTimeout 与总请求期限分开 |
| 审计保留 | 180 天 | 在线与归档均执行保留/清理策略；备份另见运维手册 |
| PAT | 默认 30 天、最大 90 天 | 一次展示、可随时撤销 |

**单行大字段限制**：JDBC getCharacterStream/getBinaryStream 不保证驱动未先物化；尤其 pgJDBC 的相关实现仍可能复制数据。4KiB 截断限制的是产品输出，不是驱动峰值。可变宽类型/表达式必须使用经验证的数据库端输出限幅或拒绝；按返回行宽预算调整 fetchSize。未知类型/不能安全限幅表达式拒绝。LOB、JSON、Unicode、重复列名、聚合/UNION 等结果投影语义的完整方案见执行器设计，M0 未证明内存界限则该路径不开放。容器内存限额只限制进程故障范围，不作为“防 OOM 已通过”的证据。

已通过身份和请求预算的 Tool 调用在入口以 request_id 唯一写入持久 `audit_outbox` START 事件，未获持久确认不进入昂贵guard处理、更不借业务连接。SQL通过后补充审批信息、执行开始时间，拒绝也写终态；同一调用不重复创建START。结束事件持久入库或加密 fsync WAL 后才返回成功；仅内存队列不算持久确认。消费者幂等更新 audit_log，崩溃遗留 START 记录恢复为 UNKNOWN 而不冒充成功。WAL/DB 均不可写时停止新 SQL，并尽力结束在途查询。所有可接纳的 Tool 调用都留事件；未认证、无法辨识的协议流量只留不含凭证的安全访问日志。

默认日志只含脱敏 SQL/指纹，不输出 token、密码、原始结果；sql_raw/sql_final 用 AES-256-GCM 信封加密并记录 key_id，解密行为本身审计。解析失败的 SQL 默认只保留哈希/长度/错误码，不能使用失败的解析器冒充可靠脱敏。

## 10. 实施阶段与验收

M0（目标第1～2周）验证模块依赖、ScopedTableBinder、对象/列绑定、MySQL+PAT+ACL+审计纵切、公开客户端完整刷新链、驱动宽行内存路径和安全版本时效。R1 的 2 个常规案例分别保留 orders/users 与 salary；4 个反例必须识别 salary，不能要求全部6例只返回 salary。

M1（目标第3～5周）完成 MySQL/PG 双方言、组织授权与事件闭环、动态池和 Schema 同步、内部回归≥300条。M2（目标第6～7周）完成四客户端矩阵与管理 API；M3（第6～8周并行）完成双视角 UI；M4（第9～10周）完成 fuzz、故障注入、压测、恢复演练与灰度。周期是计划目标，M0 通过后再承诺。

性能目标为 2C4G、50 个客户端并发、≤4KiB SQL、权限热缓存时内部非数据库处理开销 P95 <50ms；队列等待单列，不能暗中扣掉解析/授权/审计准入成本。安全目标是指定威胁模型和版本回归集通过，不声称对任意 SQL 已证明安全。

压测同时报告接纳率、配额/队列拒绝比例和等待分位数，不能仅筛选少数成功请求宣称满足50客户端负载目标。

## 11. 对 review 的细化与需要保留的验证闸门

| review 位置 | 本方案细化 | 原因 |
| --- | --- | --- |
| PG SET LOCAL 示例 | 明确先进入只读事务、业务表全限定、函数路径 pg_catalog | 事务外 SET LOCAL 不生效 |
| 公开 refresh generator | 扩展完整 token 认证/授权链与 family 墓碑 | 默认公开客户端认证入口不一定支持 refresh 请求 |
| 30 秒补扫与秒级撤销 | 主库确认最多陈旧5秒，30秒仅补偿 | 事件丢失不能突破授权时限 |
| 改密与停用 | 改密提升版本，停用才改状态 | 避免正常用户被永久停用 |
| 字符流4KiB | 区分输出限制、驱动内存与数据库端投影 | 流式API名称不代表无物化 |
| 元库与审计分区 | MySQL8.4；一期审计不分区 | 避免月分区键与全局唯一 request_id 冲突 |
| 完全限定 FROM | 同步绑定/改写所有相关列引用 | 防止改写破坏原查询语义 |
| 极短窗口重放 | 不设基于时间的无条件重放豁免 | 旧凭证重用不能直接换取新凭证 |
