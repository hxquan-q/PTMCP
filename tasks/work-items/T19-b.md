## 目标与边界

来源/父任务：T19 父任务；接续 [T19-a](T19-a.md) 的已知边界。
契约：[数据源设计](../../docs/backend/datasource.md) §5/§6/§9、[MCP Schema](../../docs/backend/mcp-tools.json)、
[API 规格](../../docs/backend/api-spec.md) 工具参数、[测试计划](../../docs/test/test-plan.md)。

目标：让已发布 PostgreSQL 数据源通过 MCP 三工具执行，而不是统一返回
`DIALECT_CONTEXT_INVALID`：

- `list_databases_and_tables`：PG 必须有 `schema_name`；目录项返回真实 database/schema；
- `get_table_schema`：按 database/schema 解析已发布快照，返回列/主键/受限外键；
- `execute_readonly_sql`：用 PG 方言 lexical policy 与 guard，`QualifiedRewriter` 只加 schema
  限定，执行前复核计划哈希/窗口/权威安全状态，结果按 PG 类型投影与既有行/格/响应预算返回。

不做项：不改变 MySQL 参数契约；不实现 Tier1 proof、并发预算/排队、PG 生产 TLS 证书夹具、
跨库查询或原始 SQL 旁路；不放宽未知语法、授权、审计或目的地策略。

不变量：PG 的 `ResourceNamespace` catalog 取已发布数据源 database，schema 取快照 schema；
授权链仍按 DATASOURCE→NAMESPACE→OBJECT 展开；PG 结果不得降级成未标注的字符串；连接仍只从
`PoolHandle` 的已激活代际借出；任何 guard/计划/安全状态失败都必须在业务连接前终止。

## 实施与验证

- `ApprovedPlanVerifier`：提取 MySQL/PG 共用的计划窗口与 SHA-256 复核；MySQL adapter 改为调用它。
- `PgApprovedQueryAdapter`：仅接受 `ApprovedSqlPlan`，复核后调用包内 `PgReadOnlyRequest.of`，
  再交给 `PgReadOnlyExecutor`；无公开字符串 SQL 入口。
- `PinnedTlsPgPoolFactory`：`sslmode=verify-full` + `sslrootcert`（`ptmcp.gateway.pg-ssl-root-cert`
  PEM）+ `PinnedPgSocketFactory` + `DestinationPolicy` 每连接重解析；缺失根证书时 PG checkout
  fail-closed，不回退到 JVM 公共信任库。`PinnedTlsPoolFactory` 按 engine 分派 MySQL/PG。
- `PoolHandle.dataSource()` 仅向受信任执行适配器暴露代际池；请求层仍不可达 DataSource。
- `McpToolService`：`requireDialect` 区分 MySQL/PG 的 schema 参数；PG 的 `GuardContext.catalog`
  取已发布 database；`relationCatalog`/`resolveNamespace` 按 engine 匹配；结果按 engine 编码。
- `ToolResultEncoder.encode(PgReadOnlyResult)`：保留 PG 类型/JSON_TEXT/BASE64 与 truncation 元数据；
  新增 `responseLimitReached` 以区分 PG 响应预算与行上限。
- 测试：`PgApprovedQueryAdapterTest` 4 例（允许/过期/篡改哈希/checkout guard）；`McpPgQueryFlowTest`
  3 例（真实 HTTP + 真实 PG：目录/表结构/类型化查询、缺 schema 拒绝）；`ToolResultEncoderTest` 1 例。

验证命令（Enter-Dev，真实 MySQL 元库 + PostgreSQL 业务容器；测试仅以测试注册表绕开生产 TLS）：

```text
mvnw.cmd -B -ntp -pl ptmcp-gateway -am verify
```
