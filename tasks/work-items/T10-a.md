## 目标与边界

来源/父任务或用户请求：[parallel-prompts-20261024](../parallel-prompts-20261024.md) A6，父任务 T10；[数据源设计](../../docs/backend/datasource.md) §1/§2/§4/§8、[总体方案](../../docs/总体方案.md) §8/§9。

目标：新建 `ptmcp-datasource` 模块，落 MySQL 只读执行协议：按数据源/配置版本建池与 generation 切换、只读事务配置、服务端游标流式读取、行上限、超时/取消、会话基线恢复、可观察状态机；模块外不存在任何接受自由 SQL 的公共执行入口。

不做项：不做 PostgreSQL 执行（B3/T11-a）；不接 guard/ApprovedQuery/HTTP/MCP 入口（C1 之后）；不做审计、租约、并发额度（B2/C2）；不做生产网络延迟注入的 M0 取消竞态实验；不改 guard、persistence、父 POM 除 `modules` 一行外的任何内容。

不变量：`ReadOnlyRequest.of` 与 `sql()`/`maxRows()` 包内可见，唯一注释指定由 T07-c 之后的 ApprovedQuery 适配器调用；执行前断言 `autocommit=true`、`readOnly=false`、catalog 等于上下文、产品为 MySQL；`SET SESSION max_execution_time`、`time_zone='+00:00'`、安全 `sql_mode`、`START TRANSACTION READ ONLY`；取数 `fetchSize=100` 且 `maxRows≤500`；会话恢复失败或取消无法确认时物理 abort 并 EVICTED；trace 不含 SQL/凭据/主机/用户名。

## 实施与验证

### 模块与依赖

`ptmcp-parent/pom.xml` 仅新增 `<module>ptmcp-datasource</module>`；新模块 POM 依赖 `ptmcp-common`、HikariCP、`mysql-connector-j`（runtime，版本均由 Spring Boot BOM 4.1.2 管理），测试依赖 JUnit Jupiter 与 Testcontainers MySQL 2.0.5；**不依赖 guard、不依赖 Spring**。

### 生产代码

```text
PoolKey                 datasourceId/configVersion/engine/host/port/database/username/credentialVersion
PoolLimits              maxPoolSize 1..8，checkout 250..30000ms，默认 3000
PoolFactory             建池抽象（测试可注入故障 DataSource）
HikariPoolFactory       仅 MYSQL；useCursorFetch/useServerPrepStmts/sslMode=REQUIRED/UTC/UTF-8
PoolHandle              ACTIVE→DRAINING→CLOSED；evict=abort+close
DataSourcePoolRegistry  按 datasourceId 单活跃池；同 key 复用；新 generation 建新池并 DRAIN 旧池
ReadOnlyRequest         final class；包内 of(sql,maxRows)；MAX_ROWS=500，MAX_SQL_CHARS=65536
ReadOnlyCancellation    取消句柄；Statement.cancel 动作加锁执行；clear(3s) 确认无在途取消
ReadOnlyResult          列/行/limitReached/trace；行深拷贝且保留 null
ExecutionState/Stage    状态机与阶段枚举
ExecutionTrace          单调时钟毫秒/阶段；poolGeneration；无 SQL
ExecutorSettings        SQL 1..60000ms（默认 15000）/取消 1..10000（3000）/清理 1..10000（2000）
MysqlReadOnlyExecutor   借连接→断言→配置→执行→流式读取→清理或淘汰；无 execute(String)
```

执行细节：

- 超时只用服务端 `max_execution_time`（设计 §8 指定的 MySQL 机制），不额外注册驱动侧 queryTimeout 取消定时器。
- 取消通过 `Statement.cancel()`；`clear` 在取消预算内等待在途取消动作结束，超时则标记 tainted。
- 错误映射到已登记码：`3024`/SQLTimeoutException/取消标志→`QUERY_TIMEOUT`/`CLIENT_CANCELLED`；`1792`、SQLState `25006`、Connector/J 只读拒绝 `S1009`→`SQL_NOT_READONLY`；先对只读事务内 UPDATE 实测得到驱动侧 `S1009`（vendor 0）。
- 正常结束：Statement/ResultSet 关闭→`rollback`→恢复 autoCommit/readOnly/networkTimeout→`max_execution_time=0`、UTC、安全 sql_mode、`SET SESSION TRANSACTION READ WRITE`→基线查询（UTC/0/0/autocommit 1）通过才 RETURNED；任一失败→EVICTED + `CLEANUP_FAILED`。
- 超时/取消：不尝试复用已中断的物理连接，直接物理 abort；调用方收到原始 `QUERY_TIMEOUT`/`CLIENT_CANCELLED`，trace 终态 EVICTED。原因见 RED 证据：Connector/J 被杀的服务端游标 fetch 会留下错位响应（下一次 SELECT 读到上一条 SET 的 OK），`rollback` 与基线无法可信恢复；[数据源设计](../../docs/backend/datasource.md) §8 明确“驱动无法提供辅助取消 join/确认机制则该组合不开放复用：超时连接一律淘汰”。

### 测试（真实 MySQL 8.4 容器，固定 digest）

`MysqlReadOnlyExecutorTest` 9 例，逐项证据：

- 只读 UPDATE：`SQL_NOT_READONLY`，表值未变；trace 阶段 `CHECKOUT→CONFIGURE→EXECUTE→DRAIN→CLEAN→RETURN`，每阶段耗时非负，trace 字符串不含表名。
- SESSION 污染（+09:00 / 99999ms）被重置为 UTC/15000/只读；归还后连接基线为 `+00:00/0/0/1`。
- 1s 超时：`SELECT SLEEP(5)`→`QUERY_TIMEOUT`；状态 `ACQUIRED→CONFIGURED→EXECUTING→CANCELLING→CLEANING→EVICTED`，evicted=1；下一请求在**不同 CONNECTION_ID**（新物理连接）上成功，证明无迟到取消误杀。
- 显式取消：300ms 后 cancel→`CLIENT_CANCELLED`，同样 EVICTED；下一请求不同 CONNECTION_ID 且返回正确值。
- 注入 rollback 失败：`CLEANUP_FAILED`/EVICTED，evicted=1；下一次得到新 CONNECTION_ID。
- generation 切换：同 key 复用同一池；credentialVersion 变化后旧池 DRAINING、拒绝新借用，新请求路由新 generation。
- 行上限与游标：120 行请求 `limitReached=true`，200 行请求返回全部 150 行且 `limitReached=false`；`Com_stmt_fetch` 计数增长证明服务端游标真实取数；`maxRows` 0/501 拒绝。
- 借池预算：池被占满 1s 预算→`CONNECTION_POOL_UNAVAILABLE`；缺失表→`DRIVER_ERROR` 且异常消息不含 SQL/驱动类名；PoolLimits/ExecutorSettings 边界拒绝。
- 所有测试使用真实容器；缺 Docker 时 Testcontainers 直接失败，不 skip。

RED（首次 `verify`，9 例中 3 失败）：

- 超时/取消：cleanup 在 `rollback` 处返回 `CLEANUP_FAILED`。
- 只读 UPDATE：映射为 `DRIVER_ERROR`（实际为 S1009）。
- 诊断：先用临时 raw JDBC 复现（已删除）：服务端超时后 `executeQuery` 抛 3024，`rollback` 再抛 3024，重试 rollback 成功后下一条 SELECT `hasResult=false`；说明被杀游标留下了多余响应包，连接协议已错位，重试只会保持偏移。`setQueryTimeout` 与 `max_execution_time` 双机制并存也不是设计要求的路径。
- 修复：删除驱动侧 queryTimeout；S1009 归入 `SQL_NOT_READONLY`；超时/取消按设计直接淘汰物理连接并保留原始错误码；`ReadOnlyCancellation.clear(3s)` 以锁确认取消动作完成，超时标记 tainted 同样淘汰。对应断言从“复用同一 CONNECTION_ID”改为“下一请求成功且 CONNECTION_ID 不同”——这是按 datasource.md §8 修正证据，不是放宽断言。

偏差与处理：A6 提示词测试项写“取消后下一请求复用连接不误杀”，本切片实测 Connector/J 无法确认被杀游标 fetch 的静默，且 [数据源设计](../../docs/backend/datasource.md) §8 明确超时连接一律淘汰；因此实现为“池复用、物理连接淘汰”，下一请求在新物理连接上执行且不被迟到取消误杀。该偏差基于实测与设计文档，未修改共享契约。
