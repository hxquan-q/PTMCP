## 目标与边界

来源/父任务或用户请求：[parallel-prompts-20261024](../parallel-prompts-20261024.md) C2，父任务 T09；[审计设计](../../docs/backend/audit.md) §3 WAL 段落、[总体方案](../../docs/总体方案.md) §9、[ADR-0007](../../docs/architecture/adr/0007-审计持久准入与非分区存储.md)。

目标：在 `ptmcp-persistence` 落地 `local.ptmcp.persistence.audit.wal` 包：TERMINAL 事件的 AES-256-GCM 加密预写日志（`TerminalWal`），每次追加 `FileChannel.force(true)`、失败即 `AUDIT_UNAVAILABLE` 且写入器不可再用；配套回放器（`WalReplayer`）按段序回放、尾帧撕裂截断到最近完整帧、中段损坏整段隔离、经 `AuditRepository.submitTerminal` 幂等入库、仅在 MySQL 提交后写 `.done` 检查点后删除段文件。

不做项：不改 B2 仓储对外行为（`AuditRepository`/`AuditTerminal`/`AuditStart` 原样）；不实现恢复调度器与 gateway 接线（后续 C1/C5 切片）；不做密钥轮换后台与多 key 存档（provider 只提供当前 key，回放不识别 key 即整段隔离）；不做 180 天保留清理；不实现 START 事件的 WAL（契约只要求 TERMINAL 补偿）。

不变量：fsync 失败必须抛出而非尽力而为；段文件任何字节不得含明文 payload（masked SQL、结果、凭证）；回放先验帧长与 GCM tag，再复验 payload SHA-256；中段损坏整段隔离重命名，不静默跳过；检查点只在 `submitTerminal` 提交确认之后；UNKNOWN 恢复（`markUnknownIfStale`）不覆盖既有 SUCCESS，WAL 晚到的 SUCCESS 对已 UNKNOWN 行报告 conflict 且不回写。

## 实施与验证

```text
ptmcp-parent/ptmcp-persistence/src/main/java/local/ptmcp/persistence/audit/wal/
  WalKey.java          AES-256 数据 key（32B）+ keyId；防御拷贝；toString 不出 key
  WalKeyProvider.java  当前 key 的函数式提供者
  WalPayload.java      AuditTerminal 的版本化 varint 二进制编解码 + SHA-256
  WalFormat.java       帧格式 [int totalLen][header][int cipherLen][cipher]，
                       header=版本/kind/eventId/requestId/seq/keyId/payloadHash(32)/nonce(12)，
                       GCM AAD 覆盖全部 header 字节；段头明文解析（magic/schema/身份/keyId）
  TerminalWal.java     段文件 wal-%06d-{bootId}.wal（CREATE_NEW 重试）、明文段头、
                       追加后 force(true)，IOException→AUDIT_UNAVAILABLE 并污染写入器；
                       包内构造器支持关闭 fsync 与自定义段上限（测试用）
  WalReplayer.java     按段序回放：尾帧不完整→truncate+force；完整但解密/哈希/结构失败
                       →整段 .quarantined；每帧经 sink.ingest 幂等入库后计数，
                       段完成后写 .done 并尝试删除段文件
```

行为：

- `append`：编码 payload → 随机 12B nonce → GCM 加密（AAD=header）→ 单次 `write` + `force(true)`。任何 `IOException` 抛 `AUDIT_UNAVAILABLE` 且写入器进入 poisoned 状态，后续 append 直接拒绝。
- 回放：`.done` 存在即跳过；段头 magic/schema 不符整段隔离；逐帧预检 total 长度（超出文件尾即视为撕裂尾，截断到上一有效帧末尾并 force），帧完整但 GCM/哈希失败或 payload 解码失败即整段隔离；未知 eventKind 也隔离。
- 入库通过 `TerminalSink.ingest`（集成中即 `submitTerminal`），`alreadyExisted` 计 duplicated；sink 抛出即中断回放且不写检查点，下次重放幂等续做。

偏差：T09-a 交接建议"复用 `AuditPayloads`"，但该类是 `audit` 包内私有、仅 JSON 序列化无解析器，跨包复用需放宽可见性或给 outbox payload 加反向解析面；本片改为 `wal` 包自带 `WalPayload` 二进制编解码（版本化、长度前缀、无 Java 反序列化入口），帧内另存 payload SHA-256 解密后复验。outbox JSON 与 WAL 二进制并存，互不影响。

## 测试与证据

`TerminalWalReplayTest` 9 例，真实 MySQL 8.4 固定 digest 容器 + `@TempDir` 真实文件系统；崩溃用分叉 JVM 子进程（`WalCrashChild`）以 `Runtime.halt(0)` 模拟，不走 shutdown hook、不 mock：

1. 正常回放 3 帧 → 3 行 SUCCESS、maskedSql 正确；第二次回放全零计数、行数不变（幂等）。
2. 子进程追加 3 帧（每帧 fsync）后 halt → 回放 3 帧全恢复、无截断。
3. 子进程 2 帧后追加半帧并 force 再 halt → 回放恢复 2 帧、truncatedBytes>0、半帧被截断。
4. 密文区翻转 1 bit（帧完整但 GCM 失败）→ 整段 `.quarantined`、0 帧入库、库 0 行。
5. 预置 `.done` → 段被跳过、0 帧入库。
6. 已 SUCCESS 行不受 `markUnknownIfStale` 影响（恢复 0 行覆盖）；仅 START 的请求被恢复为 UNKNOWN 后，WAL 晚到 SUCCESS 经回放返回 `conflict=true/alreadyExisted=true`，行保持 UNKNOWN（B2"首个持久结局为准"语义）。
7. 段字节不含 masked SQL 明文、payload 明文与 SQL 前缀（`SELECT '`）。
8. 目录被同名文件占据 → 构造即 `AUDIT_UNAVAILABLE`。
9. 段上限压到 1B 强制每帧一段 → 3 段按创建序回放、顺序与写入一致。

RED→GREEN 过程中的真实缺陷（非测试问题）：`WalFormat.decodeFrame` 的 cipher 长度校验漏算 cipherLen 字段自身 4 字节，导致所有帧在回放时被误判损坏整段隔离；以 `printStackTrace` 定位后修正为 `headerEnd + 4 + cipherLength == end`，未改任何测试断言。
