## 目标与边界

来源/父任务：[parallel-prompts-20261024](../parallel-prompts-20261024.md) C1，父任务 T07；前置 B1 已合入。契约：[sql-guard.md](../../docs/backend/sql-guard.md) §1/§7、总体方案 §8。

目标：在 `ptmcp-guard/approved` 落地守门管线的封闭末端——`GuardPipeline.guard` 依序执行 词法→语句形状→白名单→限定解析→表绑定→关系预算→列绑定→物理 READ 授权（PermissionDecider 回调）→外层 LIMIT 收紧→限定名改写→重解析与计划比对，全部通过后构造包内私有的不可变 `ApprovedQuery`。

不做项：不写执行器，不接审计；返回的 ApprovedQuery 尚无执行入口（网关未接线）；不改已冻结的 lexing/ast/scope/rewrite 既有断言（仅调用）；UNION 外层 LIMIT 仍关闭（沿用 LimitRewriter 既有语义）。

不变量：

- `ApprovedQuery` 无 public 构造器、无 setter、无反序列化入口；只能由 `guard/approved` 包内成功路径产出；executor 侧不得出现 `execute(String)`（本片不写 executor，仅约束对象封闭性）。
- `GuardContext` 字段由调用方从服务端已核实状态显式传入；本类不校验真实性，Javadoc 写明“构造者负责”；不提供 HTTP/JSON 绑定或部分更新工厂。
- 任一静态拒绝即短路：词法失败不触解析与目录查找；非 SELECT 不触绑定与授权；未知表 RESOURCE_NOT_FOUND 时授权回调零调用；授权任一拒绝即 TABLE_NOT_AUTHORIZED 且不进入改写（finalSql 不存在）。
- 请求预算只收紧：effectiveLimit = min(500, requestedMaxRows, 原外层限制)；LIMIT 0 拒绝为 SQL_UNSUPPORTED 而非签发零行审批；关系引用预算在列绑定与授权之前执行。
- finalSql 为 SHA-256 签封（sqlHash），同一输入两次 guard 的 finalSql 与 hash 稳定一致；原 SQL 不进入任何后续边界。

## 实施与验证

### 生产代码（均为本片新增）

```text
ptmcp-guard/src/main/java/local/ptmcp/guard/approved/
package-info        封闭边界说明（仅管线成功路径可产出；无执行入口）
GuardContext        主体/平台/数据源/configVersion/catalog/schema/snapshotId/resourceVersion/
                    policyEpoch/authVersion/authoritativelyCheckedAt；轻校验（非空、正数）
GuardPolicy         SqlLexicalPolicy + requestedMaxRows(1..500) + maxRelationReferences(0..64)
                    + guardVersion；mysql()/postgresql() 工厂
PermissionDecider   canRead(context, ResourceRef) 授权回调（拒绝即 TABLE_NOT_AUTHORIZED）
GuardDependencies   BoundedParser + RelationCatalog + RelationColumns + PermissionDecider + Clock
ApprovedQuery       包内私有构造；resourceRefs/sqlHash 防御性拷贝；APPROVAL_WINDOW=10s；
                    isUsable(now) 仅覆盖批准窗口，权威复查仍是 executor 职责
GuardPipeline       固定顺序管线；解析走隔离 BoundedParser；未解析关系拒绝 RESOURCE_NOT_FOUND；
                    复用 FinalSqlValidator（重解析+物理关系多重集/列来源/输出序/外层上限比对）
```

既有模块仅调用未修改：lexing/ast/scope/budget/rewrite 全部沿用 T05/T06/T07-a/b 冻结实现。

### 测试（15 用例，纯 JVM，真实 BoundedParser）

`GuardPipelineTest`（11）+ `ApprovedQueryTest`（4）：

- 快乐路径签封与字段镜像（MySQL catalog 限定 + LIMIT 500 + hash = SHA-256(finalSql) + 批准窗口）。
- 同输入两次 guard：finalSql、sqlHash、resourceRefs、effectiveLimit 完全一致。
- 授权拒绝：单关系 deny → TABLE_NOT_AUTHORIZED，回调 1 次；两关系选择性 deny 第二个 → 每个关系各问一次后停止。
- 短路顺序：词法失败（多语句）解析器/目录/授权零调用；UPDATE 被 statement gate 拒绝且不触绑定授权；未知表 RESOURCE_NOT_FOUND 授权零调用；关系预算超限在列绑定与授权之前拒绝。
- 外层上限收紧：min 语义两种组合；LIMIT 0 → SQL_UNSUPPORTED（授权已问 1 次，先于改写）。
- PG 路径：schema 限定改写（sales.orders）+ LIMIT 500。
- 封闭性：无 public 构造器、无 setter；sqlHash 双向防御拷贝；resourceRefs 不可变；过期 isUsable=false、窗口内 true。

偏差与处理：

- 授权回调先于 LIMIT 改写执行（按计划顺序），因此 LIMIT 0 用例授权先被问 1 次后拒绝为 SQL_UNSUPPORTED——短路与顺序以计划定义为准。
- 双关系选择性拒绝用例确认管线对每个物理关系各调用一次 PermissionDecider，首个拒绝即停止且不产生 finalSql。

未执行项：与真实快照存储/授权仓储的对接（网关接线片）；executor 复核链（无 executor，属后续片）。
