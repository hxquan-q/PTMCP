## 目标与边界

来源/父任务：[parallel-prompts-20261024](../parallel-prompts-20261024.md) B5，父任务 T15；前置 A5（资源表）、A6（datasource 模块）已合入。契约：[datasource.md](../../docs/backend/datasource.md) §3（异步 Job、每源仅一个 RUNNING、主库租约 + configVersion 防双 worker、staging 采集→主库事务复核→原子发布）、[db-design](../../docs/backend/db-design.md) §4、总体方案 §5。

目标：`ptmcp-persistence/schema` 落地同步 job 状态机与快照发布存储，`ptmcp-datasource/metadata` 落地 MySQL/PG 元数据采集器；发布复用 `SecurityChangeTransaction`（同元库事务内复核 configVersion→切换 active_snapshot_id→升 resourceVersion→插事件），失败整组回滚，旧快照保留。

不做项：不做触发入口（HTTP/MCP 均不接，guard 完整前无业务查询入口）；不做授权迁移（只保证删除重建产生新 generation，旧授权不继承）；不改 A6 既有执行器断言；PG/MySQL 采集之外的引擎（后续切片）。

不变量：

- 采集器只执行内建参数化 pg_catalog / information_schema 查询，标识符与注释一律视为数据，不执行、不解释任何用户输入。
- 每数据源同时最多一个活动 job（QUEUED 或 RUNNING），由 V4 `uk_metadata_sync_job_running_source`（STORED 生成列）唯一约束兜底；主库租约（lease_owner/lease_until）原子占用，过期接管必须先确认旧任务未发布。
- staging 采集全部成功才进入发布事务；发布事务内 configVersion 不一致 → RESOURCE_VERSION_CHANGED 且旧快照不动；失败保留旧快照，过期快照不得用于新查询（SCHEMA_STALE）。
- 不发布半张表：对象列数为空即跳过；超出 `MAX_OBJECTS_PER_NAMESPACE`/`MAX_COLUMNS_PER_OBJECT`/`MAX_IDENTIFIER_CHARS` 抛 METADATA_TOO_LARGE。
- `schema_snapshot` 受 `chk_schema_snapshot_expiry CHECK (expires_at > captured_at)` 约束（INSERT 与 UPDATE 均生效）。

### 关键实现事实

- `resource_object.generation` 按 namespace 内 `MAX(generation)+1` 分配（非按 object），删除重建得到新 generation/object_id，旧授权按 id 引用自然失效；无文档与此冲突，按此保留。
- PG timestamp 家族 typmod 直接存 precision（无 +4 头），varchar/bpchar 为 len+4、numeric 为 (precision<<16|scale)+4。
- MySQL 8.4：`lower_case_table_names` 仅全局可读（`@@GLOBAL.`）；`information_schema.VIEWS` 无 VIEW_SCHEMA 列，用 TABLE_SCHEMA；lctn=0 时混合大小写未加反引号即合法，引用判定只覆盖保留字与不安全字符。
- 测试断言修正：MySQL lctn=0 下 MixedCase `quoted=false` 是正确采集行为（与 PG raw≠lower 即引用不同）。

偏差与处理：

- 测试断言修正两处为采集器正确行为：MySQL lctn=0 下混合大小写无需反引号（quoted=false），引用判定只覆盖保留字与不安全字符；PG timestamp 族 typmod 直接存 precision（无 +4 头）。
- 既有类仅公开化不改语义：SecurityChangeTransaction/SecurityEvent 包私有→public（发布事务跨模块复用），datasource POM 增加 persistence 依赖。
- 修复本片实现的真实缺陷：PG 列注释误用表注释（obj_description vs col_description）、PG PK/FK 缺 WITH ORDINALITY、@@SESSION.lower_case_table_names 在 MySQL 8.4 仅全局可读、information_schema.VIEWS 无 VIEW_SCHEMA 列、checksum 类型（hex 字符串 vs BINARY(32)）、resolveObject 占位符数量。
- 环境抖动：WSL Docker 端点偶发 `Could not find a valid Docker environment` / `Communications link failure`，端点恢复后重跑全绿；未放宽断言，未跳过用例。

未执行项：CANCELLED 状态触发入口（归 T15-b API）；PG 元库承载元库角色下的同步（当前元库固定 MySQL）。
